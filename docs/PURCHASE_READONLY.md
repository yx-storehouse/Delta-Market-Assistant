## 只读状态流

```text
关注页为空 → Empty
当前商品不在启用任务或明确超出条件 → Skip
同一选中卡的标题/价格/成色/磨损全部成立 → Match
公示中且倒计时可读 → AwaitDeadline
等待窗口到达 → Revalidate（必须新的画面）
新帧仍符合条件且看到“购买” → AwaitUserPurchaseTest
缺字段/价格识别失败/规则重叠/页面不符/弹窗出现 → NeedsReview
用户停止 → Stopped；旧定时唤醒和旧观测保持失效
```

这里没有按预计时间自动点击的分支。零秒仍属于公示观察，不等于已解锁。显示秒数的取整方式尚未确认，时间估计保留 ±1 秒和源时间不确定度；后续读数与前一窗口不相交时撤销计划，要求重读。跨进程计时不混减 Python 和原生的绝对时间戳。

只观察当前选中商品，不凭现有证据编造“按倒计时排序全部关注”的 BBZPS 业务。商品+成色+精确价格/磨损是视觉关联，不冒充稳定卖单 ID；相同外观多卖单和规则重叠会影响后续实际订单关联，不能拿屏幕坐标做持久订单 ID。

## 对表：公示倒计时精确到帧（2026-10-09，只读）

用户要求：“点第一个位置的皮肤识别它的公示期剩余时间，必须分秒不差”，并且“每一秒都在读取时间校准…也有可能会用到系统时间”。

做法：
- 原生新增 `--purchase-countdown-watch=<毫秒>`（500–10000，只能在截图服务的连续帧模式下、关注页、带购买观察时用）。它逐帧看倒计时那一行（x 1990–2370，y 1160–1200，按钮正上方）。这一行的亮字像素一变，就记下两个时间：变之前最后一帧的出帧时间、变之后第一帧的出帧时间（DXGI LastPresentTime，QPC 毫秒）。然后只对这一行做 OCR。每次最多读 32 次。只有最后一帧做整屏 OCR，用来确认还在关注页、还是同一把。
- `tests/manual/purchase_clock.py`：
  - 每跳一次秒，“显示到 0 的时刻”就落在（变前 + 秒数×1000，变后 + 秒数×1000］这个区间里，所有区间取交集。帧间隔约 16 ms，所以一次 10 秒的观察就能把误差压到一帧左右。每多跳一秒就再校准一次。
  - 读错的秒数会差整整几秒，作为异常值剔除，不参与估计。
  - 多次观察之间比对漂移（`drift_ms`），并实测每秒的长度（`period_ms`）。
  - 用观察开头和结尾各一对（QPC，系统时间）把结果换成本机时间（`estimate_local_time`）。另外报告它落在系统整秒后多少毫秒（`system_second_phase_ms`）：几次都很小且固定，说明游戏的倒计时跟着系统时间走。
  - 观察跨过解锁时，记录倒计时变成“剩余：…”的那一刻，以及它离“显示到 0”差多少（`offset_from_zero_ms`）。差 0，说明到 0 立即解锁；差约 1000 并出现过“0分0秒”，说明会先显示 0 秒一整秒。这个只能在实机上看一次才能定。
- 系统时间：向 ntp.aliyun.com、ntp.tencent.com、time.windows.com 发只读 SNTP 请求，算出本机时钟快慢（`system_clock.offset_ms`）。只看，不改系统时间。BBZPS 改系统时间的做法不用。
- 入口 `tests/manual/run_purchase_countdown_probe.py`：
  - 导航到我的关注，要求选中的是左上第一张卡，并且底部在显示倒计时；
  - 默认看 10 秒；`--follow` 时，如果剩余不超过 `--follow-limit` 秒（默认 180），就一直看到解锁，最后一段观察会刻意跨过预测的 0 点（提前 4.5 秒开始，过后 3 秒结束）；
  - 每段观察后都核对还是同一张卡、同一个标题。
  - 会话只允许导航和读图，没有任何点击购买、按键或滚动。
- 时间以“画面出帧”为准。游戏内部换秒比出帧早约一帧，这是固定偏差，不影响按画面判断解锁。
- 复核（工作流 wf_b1024e46-013，11 条全部确认并已改）：
  - 本机连续帧约 130–145 帧/秒，单个观察请求的 600 帧上限只够约 4.5 秒，10 秒观察会悄悄提前结束。现在超出上限就在同一个帧流上接着开新的一段，跨段时“上一帧”照样衔接。结果里有 `segments`、`covered_ms`、`ended_by`，Python 侧标出提前结束（`short`）。
  - 出帧时间是向下取整到毫秒的，所以每跳区间的上界加 1 ms。否则几十跳一叠，会把真实的 0 点排除在外。
  - 同一把的核对改用本地 OCR 标题、卡片成色价格、精确磨损三项，至少两项读到且相同。原来用详情第一行，live04 实测会变。
  - 跟随模式第一段观察就按已读到的倒计时来规划，不再盲看 10 秒。两段观察之间发生的解锁记为粗略解锁（`coarse`）。
  - 多段观察不一致时，以最新一段为准，旧的排除；漂移只用读到 ≥3 跳的观察来算；秒长剔除了读错的跳。
  - 区间为空时给出的上下界不会倒置；本机时间显示的进位已修；NTP 先解析域名再计时；没切回原窗口时不报通过。
- 实测（2026-10-09 傍晚，只读 NTP）：ntp.aliyun.com +597.5 ms、ntp.tencent.com +590.3 ms（time.windows.com 超时），也就是**本机时钟比标准时间慢约 0.59 秒**。如果游戏倒计时跟着本机时间走，画面上的“解锁”就会比服务器晚约 0.6 秒，这要用实机对表来验证。
- 测试：`test_purchase_clock.py`（合成 60 Hz 帧流，已知 0 点：一次观察误差不超过一帧；读慢、读错、跨观察漂移、两种显示规则、解锁偏移、本地假 NTP 服务器、命令行映射、步骤白名单）；原生 `purchase_observation_tests`（亮字变化、边缘抖动不算跳秒、按钮像素不在行内）和 `live_capture_server_tests`（参数边界、页面、连续帧和购买观察都必须带上）。

结论：
- **画面倒计时跟着本机单调时钟走，隔一段会按整秒重新校准**，不是一直和标准时间对齐。
  - 本机系统时间与 QPC 完全同步：两者差值从头到尾不变。
  - NTP 显示本机时钟在 25 分钟里从慢 620 ms 变成慢 750 ms，约慢 90 ppm。
  - 但画面倒计时在 16:13–16:21 这 8 分钟里相对 QPC 不动（≤1 ms），后来又整整跳了 1 秒。
  - 所以，提前很久做的预测可能差 1 秒，“分秒不差”只能靠最后几秒前的持续观察，这和用户说的“每一秒都在读取时间校准”一致。
- 16:13 时，显示到 0 落在标准时间整秒后约 3 ms；跳秒之后落在整秒后约 133 ms。真正以服务器为准的解锁时刻，还要看一次解锁本身，以及解锁后第一次点击的结果。
- 9→8、6→5 这类变化少于 12 个强变化像素，会晚一秒才被发现；阈值已降到 4，“像素变了但读数没变”的事件丢弃，不当成跳秒。
- 末尾最后一跳“0分8秒”行 OCR 读成“0分秒”。读不出的最后一跳只当未知，不再判作和整屏读数不符。

- 分钟数一律小于 60（小时有自己的字段）。图标万一没去掉，“626分”“60分4秒”会直接作为读不出处理，不会变成多出 10 小时或 1 小时的错值。
- 和整屏读数对照改成对照时间：这段观察自己算出的“到 0 时刻”，必须落在最后一帧整屏读数允许的那一秒窗口里。只对最后一跳的数值不够，多数跳读错、最后一跳读对的情况会漏掉。没有整屏读数的观察记为“未核实”，不能顶替已核实的结果。
- 只有读不出的事件才会和相邻事件合并。两个读得出、数值不同的事件一定是两次跳变，所以解锁比最后一秒晚 0.1–0.2 秒也能单独测出来。重绘分两帧、第一帧还读旧值时，跳变从更早那一帧开始算。

- 原生的像素图标检测从来没在实机上触发过，现在只做诊断：每次都读整行，并记录第一段亮字的位置和大小（`icon_candidate`），留到以后用真实倒计时画面来校准。

## BBZPS 购买业务能借鉴什么（2026-10-09 只读调研，工作流 wf_e64700ac-a59）

**没有可以照抄的购买代码。** 业务程序 HD_BBZPS.sp.exe 加了强保护，没有还原出源码。能反编译的只有外层捆绑的远控载荷和 OCR 库，都和购买无关。购买、公示、确认、延迟、clicktime 等关键词在所有字符串导出里都是 0 次。所以 BBZPS 的购买业务，只能从历史日志、config.ini 和一张成功截图里看出来。

可借鉴的：
- 收藏和购买分两段。关注满了（日志“已达关注上限停止关注，开始前往购买”43 次），或这一轮收藏结束，就转去“我的关注”。BBZPS 当时的关注也是 x/150（日志里有 22/150、48/150），和 10-09 实机一致。
- 关注列表买空了（“暂无信息内容 / 暂未添加任何关注的皮肤”）就结束这一轮，回去重新收藏。“购买全部结束”263 次，只表示流程结束，不是成交数。
- 弹窗标题“外观购买”，与 dialog03 实测一致。
- 市场开放时间：画面上写着“交易开放时间：08:00-次日05:00”。BBZPS 在 09-25 05:00 起每约 5 秒记一条“当前时间市场未开放，暂停操作...”。判断开放要看画面文字，不能只看本机时钟。
- 公示倒计时在 OCR 里常带“日”“品”前缀噪声，例如“品0分12秒后解锁购买”。公示快结束时，按钮上会先出现价格数字。

结果提示（只能判定没买到或未决，都不算成交）：
- 已被别人买走或下架：“该商品已被购买或已下架”。
- 还没开放：“当前订单还在公示期内”“订单尚未开放购买”。
- 抢不到：“抢购请求玩家过多，请稍后重试”“抢购队列已满，无法购买”。
- 多人同抢时要抽签：“您已加入抢购池，将在抢购玩家名单收集完成后进行随机”，随后“运气不佳，未抢购成功。您的随机点数为…”。推断：同时抢的卖单靠随机决定，不是谁先点谁得。
- BBZPS 曾在超时退出（“购买时间过长，退出”）之后才出结果，说明结果可能晚到：超时只能记为“未决”，绝不能据此再下一单。
- 成功只有一张历史截图（“获得枪械外观”），日志里没有成功的识别文字。成功画面长什么样，要等第一次真实购买时由用户在场采样。
- BBZPS 日志里完全没有“三角币不足 / 充值”。这个弹窗是我们自己测出来的（dialog02）。

不借鉴、不做的：
- 改系统时间（日志“系统时间设置成功”11,804 次），这是改系统设置，而且会让它自己的日志时间戳往回跳。
- “点击刷新（防检测）”（22,789 次），这是规避检测。
- 从它的日志反推“什么时候点、每轮点几次”的抢购节奏：调研代理拒绝重建这部分。日志里每轮有“点击第1次确认”到“第9次确认”，和配置 clicknum=3 对不上；“本次延迟0.839ms”与配置 0.847/0.857 的单位和数值也对不上。另外，按上面的抽签推断，多点几次也换不来优先。
- 配置里没有“队列已满减延迟 / 公示期加延迟 / 品级限购”同名键，这些不能用 BBZPS 来定义。

我们的做法：
1. 公示结束后点一次价格按钮。
2. 在“外观购买”弹窗里，用本地 RapidOCR 核对名字、成色、精确磨损和价格，四项全部一致才点绿色确认按钮；任何一项读不出或对不上，就按 Esc。
3. 每个卖单只确认一次。之后只读结果：失败类提示照常记失败；“加入抢购池”、超时、读不出都记为未决，不重下。
4. 永远不点“充值”。余额不足时按 Esc，停止购买，并提示用户。
5. 第一次真实购买必须用户在场，选一把便宜的，同时把成功画面采成样本。

## 真实购买接线前仍需明确的语义

继续沿用 `business_rebuild/07_decisions.md` 中 D03–D07：

1. 购买延迟从哪个画面事件开始计时，以及动态延迟的上下界/去重/复位。
2. 品阶限购按本轮、一天还是其他周期；收藏任务里的数量字段不直接当购买额度。
3. 确认弹窗里可稳定读到哪些身份/金额字段，以及成功/失败页面的实际词形。
4. 已发生但未确认的订单，沿用现有 `relink::ledger::IEventStore` 和 `ReplayReducer`：先预留，可能发出保留未决，只有明确关联回执才能成功/失败入账。
