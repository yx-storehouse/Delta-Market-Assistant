# BBZPS 主业务逻辑与静态风险分析

> 分析日期：2026-10-06。对象：`C:\Users\Administrator\Desktop\price\BBZPS`。  
> 全程静态：未启动样本、未加载样本 DLL/插件、未连接样本服务器。现有 Relink Studio 0.6 源码、UI 和发布程序未修改。

## 1. 结论先说

**业务重叠度很高，但它的核心不是“价格看板”，而是“自动筛选收藏 + 关注列表公示期调度 + 购买结果处理”的双阶段自动化。**

当前目录给出了三类相互补充的证据：任务 INI、超过一千万条历史日志、已有结果截图。它们足以还原业务阶段、主要字段和异常分支；受保护的 64 位业务 EXE 尚未完整还原为源代码，所以边界比较、最后两个任务字段及延迟调整公式仍需单独确认。

**外层 EXE 还捆绑了独立的远控型载荷。** 这不是仅凭文件名或可疑 API 猜测：在外层提取出的载荷副本中，已静态反编译到隐藏 `cmd.exe`、管道输入输出、网络通信、按指令写入 Run 自启动项，以及下载文件路径。该部分应与枪皮业务完全分离。本次没有验证控制端存活，也没有判断本机当前是否已被感染。

分析证据位于 `artifacts/bbzps_static/`；取证方式见该目录 `scope.md` 和 `timeline.md`。

## 3. 主业务：两条相接的循环

以下是根据配置和历史日志还原的**业务状态图**，不是已完整恢复的函数调用图。

```text
读取方案、任务和运行参数
        ↓
识别当前页面 / 检查市场开放状态
        ↓
阶段 A：筛选并收藏
  进入典藏外观 → 设置赛季、拥有状态、品阶等筛选
  → 翻页找目标皮肤 → 设置成色、公示期、排序
  → 逐条识别价格与磨损 → 匹配规则 → 加入我的关注
  → 当前任务结束 / 关注达到上限
        ↓
阶段 B：关注列表与购买调度
  进入关注列表 → 获取列表/条目状态 → 校准时间
  → 识别公示倒计时 → 等待解锁窗口 → 确认操作
  → 观察结果：成功 / 已售出或下架 / 超时 / 页面异常
        ↓
记录、截图、退出弹窗、转下一条或重新收藏
```

### 3.1 页面识别是基础，不是只认价格

日志区分 `曼德尔`、`仓库`、`皮肤首页`、`关注列表`、`筛选`、`皮肤列表` 等页面，也有 `None` 未识别状态。

原始 OCR 记录包含文字、置信度和四点坐标；归一化记录则出现 `region`、`words`、`box`、`center`。同一流程既有全屏 `(0,0,1920,1080)` 识别，也有价格、磨损和倒计时小区域识别。截图异常记录出现 `CreateCompatibleDC failed`，支持它包含 Windows 图形截图路径，而非只从外部价格网站读数据。

**对我们项目的意义：** 需要“截图帧 → OCR 结果 → 页面状态 → 卖单对象”的适配层，不能把零散 OCR 字符串直接送给任务执行层。应保留画面时间、区域、置信度和与商品的关联。

### 3.2 阶段 A：按任务找到皮肤，再逐卖单筛选收藏

历史日志可见“处理赛季”“处理拥有情况：未拥有”“需要选择品质”“开始查找若干物品”“翻页继续查找”“所有武器都已找到”等步骤。

一个明确的价格/磨损匹配证据来自 `log/BBZ_20260924_090240.log`，按原始 LF 分隔计数：

- 第 89 行：`价格匹配: 340`。
- 第 91 行：`找到磨损值: 1.187788/1.249`。
- 第 93 行：`价格True:340 磨损True:1.187788 符合条件[1]`。
- 后续 OCR 出现 `成功添加至我的关注`。

也有“价格满足、磨损不满足，跳过收藏”和反向情况。说明它至少联合判断价格与磨损，而非只看皮肤名称。

日志还包含：

- `剩余皮肤价格高于设置价格本次收藏完毕`：存在提前结束当前收藏扫描的策略。
- `已达关注上限停止关注，开始前往购买`：关注上限会驱动从阶段 A 转到阶段 B。

是否依赖价格有序、怎样证明后续条目全部超价、上限具体数字是多少，本次证据尚未确定。移植业务设计时应先确认排序状态，避免把一个高价条目误当成整个列表已结束。

### 3.3 阶段 B：公示期倒计时与确认不是普通固定连点

日志记录了校准时间、修正剩余时间、首次检测到剩余若干秒、轨迹运行打开页面、逐次确认和二次确认等步骤。

配置中有三个时间服务器、`autotime`、`autocountdown`、`clicktime`、`clicktime2`、`clickinterval`、`clicknum`、`autoparameter`、`parameter`。历史日志还出现“当前区间为……”，支持存在参数区间/自调节逻辑。

**但未还原精确公式。** 特别是配置保存 `0.847`、`0.857`，日志却打印诸如 `本次延迟0.839ms`。该字面单位与数值含义不够一致，不能直接认定是 0.839 毫秒，也不能未经函数验证就按秒乘 1000 写入实现。

用户原 Relink 截图中的“队列已满减延迟 / 公示期加延迟”，目前在我们前端有独立字段；这份 BBZPS 的可见配置并没有相同的一组命名。它们的精确触发次数、加减方向与参数区间对应关系仍属待确认项。

### 3.4 结果处理与挂机恢复是主流程的一部分

历史证据包括：

- OCR 显示 `该商品已被购买或已下架`。
- `购买时间过长，退出`。
- `购买结果公示过长，退出`。
- `卡屏持续时间`。
- `识别结果无效(尝试 1/5)`，直到重试耗尽。
- `当前时间市场未开放，暂停操作...`。
- 已有截图显示“获得枪械外观”，包含名称、成色/磨损和时间水印。

日志中的 `购买全部结束` 是流程终止信号，**不是“全部购买成功”的凭证**；“符合条件”计数也不等于成交数。统计必须依据明确回执，区分匹配、收藏、发起、确认成功、失败和未知结果。

**最重要的数据模型修正：分开“商品”“卖单”“规则”“执行尝试”。** 同一枪皮可以同时有多个不同磨损、价格、公示时间和状态的卖单；只给商品存一条价格曲线，不足以支撑后续执行。

推荐新增对象（本轮仅提出设计，没有修改源码）：

```text
SkinCatalogEntry：名称、系列、品阶等稳定商品信息
ListingObservation：商品关联、价格、磨损、成色、公示状态、观测时间、证据帧、可信度
TaskRule：筛选条件、价格/磨损约束、数量和启用状态
TaskRun：当前阶段、已处理条目、暂停/取消/超时状态

```

若画面不给稳定卖单 ID，应明确使用“观测关联标识”，处理刷新后位置变化；不要把屏幕坐标当成永不变化的订单编号。

## 5. 值得借鉴与不宜照搬的实现

**值得借鉴：** 先收藏再调度的阶段划分、全屏与局部识别结合、页面判定后再动作、价格与磨损联合过滤、关注满额切换阶段、每次动作后看回执、超时回退和结果留证。

**不宜照搬：**

1. **改整台电脑系统时间。** 历史日志多次记载“系统时间设置成功”，随后时间戳发生回退。我们更适合保留服务器偏移估计，等待和超时使用单调时钟，不让业务校准改变系统时钟。
2. **裸用固定像素区域。** 日志含多组硬坐标。应记录窗口尺寸/DPI并校验区域变换；本轮未确认 BBZPS 对全部分辨率的适配范围。
3. **把 OCR 片段直接当金额。** 历史消息归一化统计有 9,659 条“价格解析失败”，含 `+`、字母等噪声。这是失败记录数，不是独立失败订单数。需做候选筛选、数值格式/范围校验及同一条目的字段关联。
4. **把一个高价样本当整页结束。** 原日志有提前结束策略，但排序前提未完全证明。应检查当前实际排序与列表边界。
5. **海量 INFO 输出。** 日志约 1.77 GB，原始 OCR 和倒计时记录非常密集。高频帧信息放可选诊断层，关键状态变化常驻保存，做轮转和容量限制。
6. **混淆统计。** 18,079 条“价格与磨损均满足”日志、10,225 条“二次确认”日志都不是成交数。成功统计应只从明确成功记录产生。
7. **混用时间单位。** 存储统一单位、UI 明示单位、日志输出同一单位，原样保留导入值并单独审查换算。

建议实现顺序：**任务/卖单模型 → 历史画面或日志回放测试 → 页面识别状态机 → 收藏与调度队列 → 回执账本与故障恢复**。现有 Win11 UI 只接这些模块的数据与状态；“优化”入口仍按用户约定待确认，不根据这份样本替用户臆定内容。

## 6. 远控部分：已确认与未确认

### 6.1 外层结构可直接验证

- `BBZPS.sp.exe` 文件偏移 `0x36701e` 开始的 89,976,320 字节，逐字节等于目录里的 `HD_BBZPS.sp.exe`。
- 附加数据前有 GB18030 文本 `昊帝感染分割符1昊帝感染分割符2`。这是样本内标记，不据此断言特定威胁家族归属。
- 外层偏移 `0x81a3b` 和 `0x16d04b` 另外存在两个完整 x86 PE。第二个导出 `Loader`；本轮未进一步还原该第二载荷的完整功能。
- 第一个小型 PE 的代码对其数据段前缀作 XOR 变换。按静态指令在独立字节副本上重放该数据变换，得到 920,576 字节的 `MainDll.dll` 结构；没有执行加载器。

### 6.2 已核实的代码路径

以下地址均是恢复后的 DLL 在首选基址 `0x10000000` 下的**静态地址**，不是运行时地址。

| 功能 | 静态位置与证据 | 结论 |
| --- | --- | --- |
| 指令分派 | `0x10004960` 根据输入缓冲区首字节分支；包含隐藏执行命令、创建 Shell 通道和持久化等分支 | 远控型指令处理器，不是商品筛选器 |
| 隐藏命令行 | `0x10005CE0 → 0x1000BFF0`；后者创建两组管道，指向系统 `cmd.exe`，重定向 stdin/stdout/stderr 并隐藏窗口 | 静态确认命令行会话能力 |
| 命令输出处理 | `0x1000C370` 循环读取管道并传递输出；关联网络上下文 | 支持交互式输出处理，不仅单次启动程序 |
| 自启动 | `0x10005E80` 引用 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` 并调用 `RegSetValueExA` | 存在写自启动项的代码分支 |
| 文件伪装 | 同一函数复制当前进程文件到 `C:\Program Files\Common Files\scvhost.exe` | 存在伪装路径；注意名称是 **scvhost**，不是标准 **svchost** |
| 网络连接 | `0x10009390` 构造 TCP socket 并 connect；另有 recv/send 调用及主循环 | 具备网络控制通信能力 |
| 下载路径 | `0x10006A80` 调用 `URLDownloadToFileA` 后交给后续处理 | 静态确认下载代码，不宣称当前执行过下载 |
| 剪贴板/桌面 | 有 OpenClipboard、GetClipboardData、SetClipboardData、BitBlt 的实际代码引用及鼠标/键盘相关导入 | 能力线索明确；未逐个还原完整协议 |

### 6.3 仍未确认的事项
