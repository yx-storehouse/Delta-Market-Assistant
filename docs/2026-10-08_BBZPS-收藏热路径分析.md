# BBZPS 为什么能更快进入收藏动作

> 2026-10-08；分析范围见 `artifacts/bbzps_collection_hotpath/scope.md`。本轮为业务性能逆向，flavor=null。所有样本分析均为静态，原程序没有执行，游戏没有被操作，自研程序没有再次修改。

## 1. 结论

此前“单帧采集识别降低 25.21%”并没有回答用户最关心的“选中之后为什么还迟迟不点收藏”。本次重查的是**收藏内循环与动作回执路径**，并补充了原 OCR DLL 的实际反编译证据，不再只引用一段旧日志或猜测鼠标延迟。

主要区别是处理链长度：原日志的内循环以小价格区域和固定右侧详情区域为主；自研版本仍在每个采集步骤做全屏 OCR、页面分类与局部精读，并在点星后同步执行完整回执观察。最近 26 次实际新增收藏的回执中，第一次观察全部因为“默认排序”锚点缺失而判成 unknown，随后完整读第二次。单帧去预览减少了开销，但没有消除这条重复工作链。

原日志没有鼠标按下时间戳。因此下面的 96 ms 是**价格匹配日志到价格/磨损联合匹配日志的间隔**，不是已测得的“点收藏延迟”、纯 OCR 推理耗时或端到端收藏耗时。

## 3. 原收藏内循环实际记录了什么

### F-01：价格结果之后只补一轮局部磨损读取，再做匹配

状态：validated；置信度：高，仅指已记录的事件；证据：E-02。

全量提取到 **18,079** 条 `价格True / 磨损True / 符合条件` 记录，均能与前面相同数值的价格、磨损事件配对。另有 338 条以 `价格True` 开头但不符合双 True 模式的记录没有纳入；检查样例为 `磨损False ... 不符合条件跳过收藏`，不是成功匹配丢失。

| 原日志指标 | 样本 | 中位数 | P95 | 说明 |
| --- | ---: | ---: | ---: | --- |
| 已记录价格匹配 → 联合匹配成立 | 18,079 | **96 ms** | 142 ms | 最小 44、最大 233 ms；含两条记录间发生的工作，不等于纯推理 |
| 详情 OCR 输出 → 联合匹配成立 | 18,079 | **0 ms** | 1 ms | 毫秒日志精度下，数值判断基本紧接输出；不等于 CPU 零耗时 |
| 联合匹配成立 → 下一条已记录 OCR | 18,077 | 676 ms | 1,744 ms | 不是点击延迟或回执延迟；另 2 条超过配对时间窗 |

这 18,079 个价格→匹配区间里，**每个区间都只有一条已记录 OCR，均为详情区域，没有夹入一条原点为零的大范围 OCR**。该统计的“大范围”定义是日志 ROI 的前两个坐标为 0、后两个坐标至少 1280/720；它不是推断所有未记录调用的证明。

价格 ROI 面积中位为 2,040 像素，常见范围 `(640,396,735,422)`；详情 ROI 全部是 `(1431,407,1819,640)`。其局部坐标结果与 DLL 的坐标差计算相容，但原调用入口及参数仍未直接从受保护主程序中还原。

### F-02：先有价格判断，超价不再补磨损匹配

状态：validated（日志顺序）；置信度：高；证据：E-02、前序 `P1:86–97` 定位。

2026-09-24 的具体一段：

```text
09:04:42.836  小价格区域输出 340
09:04:42.837  价格匹配 340
09:04:42.965  详情区域输出 A(1.187788)
09:04:42.966  价格与磨损联合匹配成立
09:04:43.604  下一价格区域输出 1300，记录超价结束
09:04:43.976  控件区域出现添加关注成功提示
```

原记录明确支持把价格作为先行筛选条件，再读取需要的详情。它不支持猜测两个 OCR 之间具体是哪次鼠标按下或固定 sleep，也不应把配置 `clicktime=0.0005` 直接解释成收藏点击间隔。

### F-03：下一次局部观察通常先于日志中的成功提示

状态：validated（已记录顺序），更强的“无任何同步回执”结论为未证实；证据：E-02。

18,077 条时间窗内的配对中，匹配后的下一条 OCR 都没有成功添加关注提示；常见内容是下一笔价格或当前列表区域。P1 的例子也是先记录下一价格，后出现成功提示。

这与我们“点星后先等待完整回执步骤结束，再选下一卡”的明确串行结构不同。它支持研究**局部观察和回执的较短处理路径**，但不证明原程序没有其他未记录的回读或线程，也不证明原程序不检查收藏成功。

## 4. OCR 库里真正恢复出的代码

原文件 `BBZPS/gdi32.dll` SHA-256：`5632180f33ebba6a1cc43e09ceb6e169f9a640aae7877695565c1e9d3f3fbcc8`。

以下地址是文件首选基址 `0x180000000` 下的静态地址，不是运行时地址。

### F-04：`ocrScreen` 可以直接抓所需矩形进内存

状态：validated（库内实现）；置信度：高；证据：E-03。

```text
ocrScreen @ 0x180058C90
  → sub_180051FC0
  → GetDC(NULL)
  → 宽 = 右坐标 - 左坐标，高 = 下坐标 - 上坐标
  → CreateCompatibleBitmap(宽, 高)
  → BitBlt(指定屏幕矩形)
  → GetBitmapBits(内存像素)
  → 颜色/图像矩阵处理
  → 调用持有的识别对象虚函数（0x18005309E）
  → 结果格式化（0x1800530C1）
```

关键调用点：`0x18005249D / 0x1800524C2 / 0x180052503 / 0x180052582`。这不只是导出名字猜测，已取得实际指令反编译路径。所需像素在内存里传递；调用方不必先把整屏截图写成 PNG 文件再交给此入口。

**不要扩大该结论：** 此版本仍会每次创建并释放 GDI DC/位图，不能说它已复用全部抓屏资源。完整屏幕入口没有直接 `Sleep` 调用，不等于调用方没有等待；库内还存在可选参数和其他处理路径，不能据此保证所有配置下都无文件操作。

另一个入口 `ocrWindow @ 0x180058CD0 → 0x180050400` 则使用 `PrintWindow` 后裁区，并含特定窗口处理分支的 30 ms Sleep。我们没有拿到受保护业务主体对两种入口的真实调用点，不能声称 BBZPS 每次一定走 `ocrScreen` 而不是 `ocrWindow`。

### F-05：模型实例有一次初始化与借还结构

状态：validated（库内设计）；置信度：高；证据：E-04。

- `init/initTomato @ 0x180057EE0` 使用 `dword_1806E2800 != 1` 门控，加载 det/rec/cls 等资源，创建并保存实例，完成后标记已初始化。
- `startLock @ 0x180058610` 从已有实例表找空闲项并标记占用。
- `unlock/stopLock @ 0x1800590D0` 标记该实例可用并通知等待者，而不是销毁整个模型。
- `release @ 0x180058850` 才走释放并重置初始化标记的路径。
- `0x180046BB0 → 0x1800470A0 → 0x18001EB20` 中存在持有的预测器对象；初始化与每次 ROI 识别分开。

但**自研当前模型/helper 也已经常驻**，不是每条 ROI 都重新启动。不能把这个旧问题再次当成当前慢的主要原因。

同时，库里有数字模型和 `setRunMode` 等入口，但没有证据证明原收藏实际选择了纯数字模型、跳过检测或某种 fast 模式。已恢复构造器中的默认字符串反而是 `slow`；只看存在 fast 接口就宣称调用了 fast 属于过度推断。

## 5. 自研收藏卡在哪里

### F-06：最近实际新增收藏，26 次回执全部先失败一次再完整读取

状态：validated（历史实机记录）；置信度：高；证据：E-05。

| 指标 | 实际结果 |
| --- | --- |
| 来源 | `white_star_run_06` 的 21 次、run07 的 3 次、run08 的 2 次 |
| 成功回执 | 26 |
| 每个回执实际采集次数 | **全部为 2 次** |
| 第一帧页面错误 | **全部 `E_PAGE_INSUFFICIENT_ANCHORS`** |
| 第一帧默认排序锚点 | **全部缺失** |
| 第一轮被丢弃采集耗时中位数 | **531 ms** |
| 完整回执步骤耗时中位数 | **1,640.5 ms** |
| 点星步骤开始至回执中位数 | **2,086.5 ms**，包含轨迹及等待，不是鼠标按下时刻 |
| 点星轨迹中位数 | 231.5 ms |

第一帧并非“不管匹配直接点错”：我们的代码确实停止放行并补读。但性能问题是，局部反馈过程中一个排序标签未认到，会让整次页面识别变成 unknown，随后又跑一次完整观察。原来的单帧减负没有处理这个“正常反馈过程中重复跑大流程”的问题。

**时间范围必须分清：** 这 26 次属于去预览/去重复文字之前的真实收藏记录。去除冗余后的 `ab05` 只是固定卡片读取测试，没有点星；本轮也没有再次实机点星。因此不能把 1,640.5 ms 宣称为修改后最新回执耗时，或保证新版仍必然 26/26 重读。可以确认的是相关全屏分类和串行回执结构在当前源码中仍存在。

### F-07：当前还在每一帧做大范围处理

状态：validated（当前源码）；置信度：高；证据：E-06。

- `src/diagnostics/live_capture_check.cpp:201`：每次 `--ocr` 先调用 `recognizer.recognizeFrame(ocrFrame)`，之后才分派局部读数。
- `src/application/vision/dxgi_observation_source.cpp:120/141/147/181`：每次 capture 中创建 factory、D3D device、duplication、staging。不能把约 180 ms 抓帧总耗时全部归因于某一个调用，但生命周期确实仍是逐次创建。
- `tests/manual/run_collection_trial.py:698–715`：选卡 → 联合匹配/点星 → 同步 capture 回执；下一卡要等本次回执结束。
- `tests/manual/collection_live_session.py:1067`：当前动态等待为选卡 120 ms、点星 80 ms、滚动 180 ms；加上鼠标轨迹与后续观察。不是简单存在一个任意的“收藏等待 2 秒”参数。

## 6. 应该借鉴什么，而不是盲目把延迟归零

这里是基于新证据形成的后续设计要求，不是已经交付的新提速代码。

1. **进入页面、切商品、切成色、滚动后做完整校准；稳定列表内走短路径。** 新帧只读取当前需要的价格、磨损、标题/局部身份锚点与星标，不每次重复整屏 OCR。任何窗口、内容、选中态或几何变化都使上下文失效并重新校准。
2. **价格先行。** 可由当前可信卡片区域确认超价时，保留原有序边界规则停止；没有必要先重复读取不再用于决策的磨损。不能从旧价格、历史记录或旧坐标推断当前条目。
3. **将回执读成回执，而不是重走全部页面识别。** 点星后对已派发的那一项做同帧局部身份、金星和成功反馈校验，短小有界轮询；保留 journal、真实回执和超时未知状态，别靠删掉确认换速度。
4. **采集资源复用和内存 ROI 传输单独落地。** 常驻采集对象，按需求传局部像素；仍校验真实目标、帧龄、源帧关联和资源释放。不是加载原 DLL，也不是无脑常抓整屏。
5. **鼠标轨迹先保留。** 当前最大的已见差距在全屏处理和回执重读，不应先撤销轨迹或身份检查。原鼠标轨迹/按下延迟没有函数级证据，先不假称“照搬原参数”。

验收应分三条独立计时：选卡输入完成→满足条件后发出点星；点星发出→回执确认；整项开始→下一项开始。每条都统计采集次数、失败重读、轨迹与等待。继续只拿固定画面单帧 A/B 作完整收藏提速结论会再次偏题。
