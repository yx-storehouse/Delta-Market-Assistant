# 收藏提速：耗时拆解与改进方案（2026-10-08）

> 更新：6 项已全部实现并离线发布，见 `docs/COLLECTION_PIPELINE_SPEED.md`；实机待测。

只读分析，没有改代码，没有操作游戏。数据来自 `artifacts/collection_tail_latency/run04`、`run06` 的 session.steps，共 90 个完整“选卡→点星→回执”周期。脚本与原始输出在 `artifacts/collection_speed_plan/`。

## 一把约 984 ms 花在哪（run06 中位，run04 基本一致）

| 段 | 中位 ms | 性质 |
|---|---:|---|
| 选卡鼠标轨迹 + 按住 | 58 + 32 | 动作 |
| 抬起 → 首帧看到选中 | 243 | 游戏响应约 180–240 + 轮询粒度 64 ms |
| 选中帧 → 识别结果返回 | 157 | 4 个列表区 OCR 串行 92 + 标题 25 + 价格 22 |
| 结果返回 → 点星开始移动 | 31 + 79 | Python 记账（journal 全目录扫描 2 次、步骤 JSON + fsync） |
| 点星鼠标轨迹 | 60 | 动作 |
| 点星 → 回执完成 | 265 | 首帧在 62 ms 就已是金星（93/93 次），其余约 160 ms 是又一遍整页 OCR |
| 回执 → 下一卡 | 16 | |

翻页每 4 把一次，每次约 1.3 s：滚动前移动用 standard 轨迹 264 ms、固定等待 187 ms、稳定判定按 65 ms 一帧采 6 帧、再整页 OCR 约 276 ms。平摊下来每把还要多约 320 ms，所以实际约 1.3 s/把。

参考：BBZPS 日志里“匹配成立 → 下一条 OCR”中位 676 ms，加上价格→匹配 96 ms，约 0.77 s/把。

## 改进项（按收益 / 风险排序）

1. **热路径去掉记账开销，约省 95 ms/把，不改业务。**
   `decision_records()` 和 `prepare()` 每次都对整个 journal 目录逐个文件 CreateFile 取元数据，实测各约 19 ms（453 条），并且随记录数线性增长。会话独占写入期间维护内存索引，只检查新增文件。session 步骤 JSON（约 300 KB、indent=2、每步 2–3 次 fsync）改为后台线程写。点击前必须落盘的只有 journal 的 prepared 记录。
2. **回执改为同卡局部像素确认，约省 170 ms/把。**
   93 次回执的第一帧已经是金星，后面约 160 ms 都在重读整页文字。改为同一张卡的星标像素白→金，加原生边线确认卡片位置没变；整页 OCR 只在翻页或出现异常时做。需要调整此前自定的“局部回执不能升级成可继续点击的完整布局”约束，下一张卡的价格、成色、磨损仍在它自己的选中帧里重读。
3. **选中后只读需要的区域，并行 OCR，约省 90–110 ms/把。**
   每次选中都串行重读 4 个列表区（约 85 个字），只为证明页面没变。改为每页校准一次，之后用像素布局一致性代替；必须读的标题、价格、磨损三个 ROI 并行识别。
4. **就绪轮询只拷 ROI，约省 40–60 ms/把，翻页也受益。**
   每次轮询都把 2560×1440 整帧拷到 CPU（`dxgi_observation_source.cpp:248` 至 `:266`，约 31 ms），再做整帧 digest 和判定，所以一轮 64 ms。只拷选中卡和详情区，轮询能跟上游戏帧率。
5. **翻页提速，每次约省 0.9 s，平摊约 220 ms/把。**
   滚动前移动改用收藏的 continuous 轨迹（264 → 约 60 ms）；去掉 180 ms 固定等待，已有稳定判定兜底；稳定判定用 ROI 快速轮询；整页 OCR 并行。
6. **（需要你拍板）点星后不等回执就移向下一张。**
   在下一次选卡按下前，用像素确认上一张已经变金星；没确认就不按。这样会改变现在“有未决就禁止任何输入”的规则，约再省 60–80 ms/把。

## 预估

- 1–5 做完：页内约 0.5 s/把，算上翻页约 0.6 s/把，约 1.6 把/秒，是现在的 2 倍左右。
- 再加第 6 项：约 0.43 s/把，约 2 把/秒以上。
- 硬下限是游戏选中响应（约 200 ms）加两段鼠标轨迹（约 120 ms），每把约 0.35 s。

以上是离线推算，每一项落地后都要用新的 S11 实测记账，不能当作已达成。
