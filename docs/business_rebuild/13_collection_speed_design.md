# 收藏价格识别修复与提速设计

> 实施后结果已推进，见 [提速实机验收](../COLLECTION_SPEED.md)。本页下文“当前/最新失败”专指设计审计时的修复前基线，不覆盖新的实测结果。

本页记录修复前的实测基线、BBZPS 原日志可复用的处理顺序，以及本轮优化的验收合同；不是优化后验收报告。当前最新验收在第 21 行价格识别失败，已完成 18/21 条启用规则。旧 `run_12` 成功记录属于此前开发周期，不覆盖这次验收失败。

完整机器证据见 [reference_review.json](../../artifacts/collection_speed/reference_review.json)；所有采样来自已保存文本日志。本次设计审计没有启动 BBZPS、没有操作游戏、没有保存游戏图像。

## 1. 先修识别，再减少固定开销

最新验收中，采集与识别占 64.2%，输入后等待占 23.61%，鼠标轨迹占 9.45%。因此保留轨迹并先处理诊断/OCR 冷启动与统一等待，比只缩短鼠标移动更切合实际瓶颈。价格失败则是另一项可靠性问题：同帧测得三个满足可靠字块合同的组件，OCR 结果却没有完整给出数字；三次价格精读仅耗时 3、6、2 毫秒，并非该小区域本身计算太慢。

原业务的商品、成色、价格和磨损联合判定、既有关注保护、新帧回执及账本不作为删减对象。优化沿用现有业务调度，不重写收藏流程，不改为购买流程。

## 2. BBZPS 的哪些做法有真实依据

已经重新执行只读校验：`analyze_startup_flow.py --verify-only` 输出 `PASS`，1,192 条原日志字节定位全部吻合。原证据和含义继续使用 [首次启动重建](10_bbzps_first_startup_reconstruction.md)，[旧性能审计](11_bbzps_collection_alignment_performance.md) 中“空关注”“只支持两卡”“每 ROI 冷启动”等是历史状态，不再作为当前实现描述。

| 原日志证据 | 实际支持的结论 | 在新实现中的处理 |
| --- | --- | --- |
| P1:73–75 | 小价格 ROI 读到 1800 后结束该条件扫描 | 保留原超价停止边界；不声称市场尾部穷尽 |
| P1:86–89 | 价格 ROI 有杂项 `+3` 与 340，后续价格匹配为 340 | 识别 ROI 与业务值分开；不能照搬任意杂项过滤来猜价格 |
| P1:90–93 | 详情 ROI 读取磨损后进行价格/磨损联合匹配 | 保留同一选中卡身份、成色、价格、磨损绑定 |
| P1:94–97 | 接着读取下一价格，后续控件观察出现添加关注成功提示 | 可研究按步骤减少 OCR；日志不足以证明原程序每次点击的阻塞方式 |
| P1/P2 与运行入口分布 | 根据当前页面接续，而不是每次强制回首页 | 沿用已有检查点与当前页导航，不重新开始所有任务 |

P1 指 `BBZPS/log/BBZ_20260924_090240.log`。机器报告保存相关原行时间、字节偏移和 SHA-256，便于复核。日志时间只是历史事件时间；没有同硬件、同配置、同挂单的运行对照，故本页不声明“BBZPS 比新版本快多少倍”，也不把日志间隔当作某一函数的真实推理耗时。

## 3. 实施顺序和不变合同

| 优先级 | 修改对象 | 具体方案 | 验收点 |
| --- | --- | --- | --- |
| P0 | 价格识别 | 保留原始像素；对固定预处理与固定 provider 做实验，输出真实纯数字及词框 | 原失败像素或新同帧采样读出完整价格；不得字符替换、配置补位、按价格挑模型 |
| P1 | native 诊断/OCR 生命周期 | 一个连续业务段复用诊断进程、helper 与语言引擎；每请求仍拿新帧 | 多次 capture 的 PID/启动标记证明复用；请求编号、超时、取消及退出排空验证通过 |
| P2 | 采集初始化 | 评估复用 DXGI 采集对象；处理尺寸变化、失效与资源释放 | 新帧与 viewport 绑定保持；图像不落盘；失效时明确重建而非返回旧帧 |
| P3 | 步骤所需 OCR | 分清目录、筛选、所选卡与回执；避免普通步骤无用的宽 OCR/预览编码 | 模态、标题、几何、选中卡和回执仍有对应新帧证据；receipt-only 不用于下一卡输入 |
| P4 | 固定等待 | 用有界新帧就绪验证替代统一 600 ms；按动作类型记录等待与重试 | 动画未结束就继续等待；超时停止；不放宽 5 秒帧龄，不把等待改短后盲点下一步 |
| P5 | 实机验收 | 从最新未完成第 21 行恢复，继而跑代表性的完整新周期 | 保留所有旧关注和 journal；验证 480 正确触发原超价边界；核对最后三条规则 |

常驻化不是无限缓存：每个结果必须属于本次请求、本次 HWND/viewport 和新 frame_id；旧采样的标题、卡片坐标与 ROI 租约不得因“同商品”直接跨动作沿用。输入仍依附前台所有权与用户干扰检查；整段开始前置一次，结束或异常恢复 IDE 一次。

模型初始化应在实机段开始前完成并单独计时。第一帧冷启动与后续稳态分别披露；不能只给缓存热态数字而隐去首帧，也不能把模型初始化重复加到它本已包含的总耗时上。

## 5. 如何复算与比较

下面命令只读历史文本，不连接游戏。输出放在新的 `collection_speed`，不覆盖旧验收或旧完整周期报告。

```powershell
python -X utf8 docs/business_rebuild/scripts/analyze_startup_flow.py --verify-only
python -X utf8 artifacts/collection_speed/compare_runs.py --self-test
python -X utf8 artifacts/collection_speed/compare_runs.py --before artifacts/collection_acceptance/run_01 --output artifacts/collection_speed/baseline_timing.json
python -X utf8 artifacts/collection_speed/build_reference_review.py
```

`compare_runs.py` 支持可选 `--after` 参数指向新完成的运行目录。脚本验证 session 与独立 step 文件逐项相等、事件计数一致、串行时间不重叠，且只计一次 `capture_attempts`。每份结果携带输入文件哈希；对比输出捕获、轨迹、等待、点星到回执、显式选卡到回执的中位数和 P95，不以两个不同长度的市场扫描总耗时直接推导倍数。

常驻版本中 helper 的启动计数可能是进程累计值。脚本将其标为 `helper_start_count_raw_sum` 并明确不当作真实启动次数，另保留 PID 身份与全帧 `helper_reused`/冷启动观测。新增采集计时应给出字段定义，避免同名字段悄悄改变统计口径。
