## 1. 结论与当前完成状态

**实测慢既有诊断等待，也有当前实现的真实开销，不是已经优化好的成品被人为限速。**实际收藏使用人工联调驱动：每两张卡启动短批次，每次观察重新启动程序，每个 OCR 区域又单次启动 PowerShell 和 Windows OCR 引擎。业务规格已有原记录支撑，但完整的常驻收藏执行器尚未接入普通程序界面；如果原样把这条链装进成品，慢的问题仍然存在。

本轮重新核对收藏全部分支、源代码和已有计时，产出可重复的离线耗时审计；**没有修改游戏执行代码，没有完成提速，也没有再次操作游戏**。本次变化为文档、审计脚本与其回归测试，不重新标记或替换已验收的程序二进制。原软件仅作为日志/既有静态证据来源，没有执行。

- 当前现场以 `artifacts/m2_savedvalue_collection/current_checkpoint.json` 为准：最后观察为 **空关注**，`cursor_valid=false`。旧 P90 B 第六卡不再是当前可用位置。
- 历史确认收藏 25 次是动作历史，不是当前关注数量。本轮不推断这些条目为何不再显示。
- 正式配置已导入 50 条任务、21 条启用、9 个启用商品；全部任务含 13 个商品。目录 149 项。导入配置已经完成，不等于真实执行器已消费 UI 中后续编辑的任务。
- 采购在原流程的后续关注处理阶段。当前只对齐收藏与阶段交接，不把进入收藏商品卖单页的导航文字当作购买成交。

### 2.1 不要把配置导入和实际执行来源混淆

当前 `build_collection_plan.py:8、20–23` 仍固定读取历史 `task_snapshot.json`；`run_foreground_batch.py:169–173` 又读取该快照并要求不限量。GUI 的真实目录/导入/持久化已完成，但运行器尚未从当前 AppState/持久化任务创建不可变运行快照。后续用户编辑最高价或新增赛季后，要从**当前配置**冻结本次任务，保留源行与导入哈希作为来源，不能继续把旧快照当成新配置。

进度应保持五层：`运行快照 → 赛季/筛选组 → 未完成商品集合 → 商品内成色规则 → 卖单位置与动作账本`。分组键未还原的部分明确保留，不能随意按商品名排序冒充原程序。

## 3. 实际有多慢：只使用已保存的收藏样本

样本为 `artifacts/m2_savedvalue_collection/live_series_s6_v5/live_1.json` 至 `live_5.json`。外层 `result` 与最后一次 `attempts[].result` 重复，统计时只计一次；实际重试仍逐次保留。逐帧值、原文件 SHA-256、各批关联 journal 位于 `artifacts/collection_alignment_audit/timing.json`。

| 指标 | n | 最小值 | 中位数 | P95 | 最大值 |
|---|---:|---:|---:|---:|---:|
| `frames[].capture_ms`，毫秒 | 20 | 198 | 213.5 | 240 | 295 |
| `ocr.frame_age_at_result_ms`，毫秒 | 20 | 1,414 | 3,028.5 | 3,079 | 3,405 |

P95 采用 nearest-rank。第二行是**源画面呈现到整套 OCR/ROI/解析结束的年龄**，不是纯整帧 OCR、单个模型推理或单次进程启动的耗时。它与 capture_ms 起点不同，不能直接相减命名为“纯 OCR”。

| 收藏批次 | 观察次数 | journal 确认新增 | 游戏前台驻留 |
|---|---:|---:|---:|
| `live_1` | 2 | 0 | 8.453 秒 |
| `live_2` | 5 | 1 | 17.625 秒 |
| `live_3` | 5 | 2 | 20.937 秒 |
| `live_4` | 5 | 2 | 20.718 秒 |
| `live_5` | 3 | 1 | 12.469 秒 |

这些前台驻留值来自 10 ms 采样的 monotonic 时间记录；不是完整进程起止墙钟。两个两卡成功批次的 **20.7–20.9 秒**足以证实当前链条真实偏慢，不能称作“用户感觉慢而程序已经很快”。这些是既有版本、有限卡位与识别条件下的历史批次，不是当前发布版完整功能性能跑分，更不是 BBZPS 与新软件在同环境下的对照实验。

## 4. 慢在哪里

### 4.1 确实加了等待，但它只解释一部分

| 代码 | 当前实际含义 |
|---|---|
| `run_foreground_batch.py:84` | 每批游戏前置后实际等待 0.9 秒 |
| `run_foreground_batch.py:223` | 每次输入后通常等待 0.6 秒；选卡与点星两次通常共 1.2 秒 |
| `run_foreground_batch.py:92–100` | 只有 neutral_pointer 开启才另等 0.15 秒 |
| `foreground_batch_core.py:27–40` | 仅 unknown 页类时有界新帧重读，间隔最多 0.15 秒，不固定重读三遍 |
| `run_foreground_batch.py:190` | 7 秒是动作后回读的剩余预算要求，**不是 sleep(7)** |
| `run_foreground_batch.py:187` | 5,000 ms 是帧龄上界，**不是等待** |
| 批次 30 秒、子进程 20/50 秒、系列 900 秒 | 都是超时/截止时间，不能相加成主动等待 |

### 4.2 更大的结构性问题是反复冷启动与宽识别

1. `run_collection_rows.py:36–39、67–69` 每两张卡重新启动 Python 批次；每批查窗口、前置游戏、末尾恢复 IDE。这已经不是每动作切换，但仍不是完整连续业务段持有前台，与用户要求还有差距。
2. `run_foreground_batch.py:101–112` 每次观察启动一遍 `RelinkStudio.exe --live-capture-check`。两卡新收藏通常需入口观察一次、每卡选中后一次、每卡回执一次，共五次。
3. `windows_ocr.cpp:150–170、204–247` 每个 ROI 都进入一次 `recognizeFrame`，新建共享内存和 PowerShell 进程；`windows_ocr_worker.ps1:12、25–33、81–82` 只处理一条请求，每次新建 OCR 引擎，输出后退出。
4. `live_capture_check.cpp:163–188、230–269` 先全屏，再列表锚点、控件、标题、详情、英文精细详情、卡片字段；空字段另拆两块读。正常收藏列表不带通用 UI ROI 时共 **6～10 次** OCR 调用。v5 两个两卡批次每次观察实际为 1 整帧 + 1 锚点补读 + 5 字段，因此由记录与源码推导每批 **35 次** one-shot OCR 调用；这不是独立计时测出的冷启动耗时。
5. `selected_detail_precise` 目前无条件做，而非只在中文数字歧义时做。诊断预览还编码 PNG/Base64，再由 Python 转 JPEG；图片没有落盘，但编码和跨进程传递仍占时间。
6. `dxgi_observation_source.cpp:119–147` 每次 capture 也创建 factory、D3D device 和 duplication；已有约 0.2 秒 capture 并非可复用会话的极限。

没有记录每个 ROI、引擎创建、进程启动或纯 RecognizeAsync 的耗时，当前证据只支持定位架构开销，不能把约 3 秒全部归因某一个组件。动作 journal 的少量文本持久化是防重复切星机制；它不是反复把游戏截图写盘，更不应通过删掉 journal 来“提速”。

### 4.3 已有传输框架，但还没有真实常驻 OCR 服务

`WorkerProcess` 已有 start/send/poll/shutdown 和共享帧租约；测试 worker 的 provider 为 synthetic，返回像素哈希，不是 OCR。live 只使用 WindowsOcrRecognizer，没有接入它。

接入前有两项真实协议差异：`worker_protocol.cpp:288–292` 要求 token 有 numeric score，而 Windows OCR 没有此置信度；`:246–253` 要求 model_sha256，而系统 OCR 并未提供可直接当成模型文件的工件。因此需要版本化表达“置信度不可用”和可核验 provider 身份，不能填假分数或假模型哈希。

还发现计时正确性问题：`live_capture_check.cpp:371` 在 preview 编码和进程输出前记录年龄；runner 接收结果后才记 `previous_received`，两者之间尾段未计入动作年龄。后续性能实现应从协调端保守计入完整响应时间，或建立真实共享单调时钟契约；不能靠放宽 5 秒门槛掩盖旧帧。

## 5. 实施顺序与验收条件

这里是已对齐的开发要求，不是本轮已经交付的运行能力。

| 顺序 | 改动 | 通过条件 |
|---|---|---|
| 1 | 增加 capture、helper start、ROI、等待、输入、回读、完整响应分段计时；修正尾段年龄口径 | 每次字段有帧身份和计时定义；重试/失败不漏记；不以假 score 获得协议通过 |
| 2 | 在现有协议/共享内存基础上增加真实常驻 OCR provider，按语言缓存引擎；连续业务保留采集会话 | 多次观察不重复冷启动引擎；取消/超时/崩溃后租约正确释放；不产生游戏图片文件 |
| 3 | 同一帧只读当前步骤所需 ROI，必要时再精读；正常运行不逐卡编码预览 | 缺小数点、价格杂字符、标题冲突、过期帧等现有负例仍被阻断；回执使用新帧，不能复用动作前图 |
| 4 | 按第 2 节逐项接入完整收藏协调器，从当前配置冻结任务并恢复五层进度 | 空关注回退、非空分支、筛选差异、未找到商品、目录翻页、成色/仅磨损、非零限量、跨季、满额均有可回放分支 |
| 5 | 生产者输出动态完整卡片/半行/滚动条几何，runner 接入 frame-local lease | 滚动后全部坐标重新绑定；半行拒绝；真实滚动条位移证明进度；六卡结束不冒充扫描完成 |
| 6 | 一整个连续业务段持有前台，观察到页面就绪后继续，替代统一 0.6 秒 | 不按卡片小批来回闪屏；用户切走就停；结束/异常统一恢复 IDE；不给未就绪页面发送输入 |
| 7 | 在相同任务、相同画面条件下跑修复前后对照 | 分别报告启动、首次观察、稳态选卡到确认、两卡批次与异常率；有实际数据再给速度，不先承诺秒数 |

不能通过删掉商品身份复核、同帧联合匹配、既有金星保护、动作前 journal 或新帧回执来换速度。观察步骤的结果可以复用；跨动作的旧图和旧坐标不可以复用。原日志未证实的分组键、价格等值边界、默认排序全局单调性和全部内部点击策略继续保持未决。
