# BBZPS 首次启动与首轮业务：按原记录逐步复刻

> 复核日期：2026-10-07。本文取代“启动后直接进入普通交易行、再从头收藏”的简化描述。目标是复刻 BBZPS 已证实的业务顺序、页面回读和分支，不重新发明业务。保留现有 Win11 白灰 UI 与模块边界。
>
> **最重要的修正：先判断当前页面；典藏外观入口存在先检查“我的关注”的路径；已有皮肤列表可以直接接续处理。收藏不是每次运行的固定第一阶段。**

## 1. 本次究竟重新看了什么

本次重新逐行扫描了 `BBZPS/log/` 的 **15 个文件、1,774,992,038 字节、10,576,696 个 LF 分隔行**，不是只复述上一次的摘要。其中 2 个日志为空。记录中有 **97 次“开始执行: 全自动皮肤”以及 3 次“开始执行: 发送测试”**。这是运行入口消息数量，不是 100 次进程冷启动，也不是 100 次成功业务。

- 机器证据：[startup_flow_evidence.json](evidence/startup_flow_evidence.json)。包括完整源日志 SHA-256、运行入口、早期页面序列、业务事件见证、选定 OCR 锚点。
- 每条见证包含原文件、**原始 LF 行号、字节偏移、字节长度、原行 SHA-256**；复验脚本重新打开原文件逐项比对。
- 逐行查看工具：[inspect_startup_log.py](scripts/inspect_startup_log.py)；全量重建与证据复验：[analyze_startup_flow.py](scripts/analyze_startup_flow.py)。脚本只读文本，不导入样本的 Python 模块或 DLL。
- 配置与二进制前序证据仍引用 [原静态报告](evidence/static-analysis-report.md) 与 `artifacts/bbzps_static/configs_redacted.json`，不把 DLL 导出推断成已经恢复的完整函数调用链。
- 本次没有启动 BBZPS。当前自研程序的真实采集验证与本文的历史行为复核是两个独立证据来源，不混写成原程序实测。

## 2. 先分清三种“首次启动”

### 2.1 双击 EXE 到主窗口出现

当前证据确认外层 x86 包装文件包含内层 x64 文件；存在 `userinfo` 配置、`autologin` 开关和授权库接口；业务配置具有 `[MainWindow]`、`[GlobalSettings]`、`[SkinTasks]` 三组。**这些结构不证明主窗口初始化函数的实际调用顺序。**

| 层次 | 已确认内容 | 仍缺的细节 |
|---|---|---|
| 包装入口 | 外层文件与内层主体的静态关系已建立 | 外层到业务主窗口的完整正常分支调用栈 |
| 登录层 | 两份 `*.exe.ini` 均有 `autologin`、用户名和密码字段；本次不导出凭据 | 登录成功/失败 UI、首次安装与已有配置的差别、重试/超时 |
| 业务配置 | MainWindow.mode；全局参数；13 列任务；运行参数 | 默认值生成顺序、缺文件/损坏文件处理、方案切换精确实现 |
| 主窗口 | 现有任务/运行参数与历史任务行为对应 | 精确控件对象名、首次显示时自动勾选和按钮事件绑定 |
| 外层附加支路 | 前序分析已经单独识别远控型载荷 | 该支路不属于枪皮业务复刻目标；本文不复制它 |

所以本文不会声称“冷启动每一个内部函数已经还原”。下面详细复刻的是证据充分的 **点击开始后的业务启动，以及首轮流程**。

### 2.2 点击开始运行：首次健康检查不是只执行一次

P1 第 1 行和第 28105 行都出现“开始首次服务器健康度检查”，后者是同一日志里的又一次运行。全量扫描得到 97 条这种消息，与 97 次“全自动皮肤”入口同量，但不能仅由计数推导严格一一对应函数。

**复刻要求：**把它视为“该次业务运行的初始化线索”，而不是硬编码成首次安装才执行。日志文件名的时间也不是第一条业务日志的时间；例如 P1 文件名含 `090240`，第一条记录实际为 **2026-09-24 09:03:57.738**，不得把两者之差写成固定启动等待。

### 2.3 已在业务页时再次运行

首次观测页的分布如下，覆盖全部 100 个运行入口消息；其中 `发送测试` 不属于完整皮肤流程，缺页记录也不补造。

## 3. 原页面名不要按字面误解

1. P1 第 11 行 OCR 实际有“开始游戏、仓库、特勤处”等大厅导航，第 13 行分类结果却是“曼德尔”；第 20 行 OCR 才出现“曼德尔砖、典藏外观、典藏挂饰”，第 22 行仍叫“曼德尔”。**同一日志标签不能直接当成单一视觉页面的真值。**
2. P1 第 1795 行显示混合枪皮、`我的关注：48/150`、公示倒计时，第 1797 行分类仍是“皮肤列表”。也就是说，**“皮肤列表”标签可能覆盖关注内的在售列表**。
3. 顶部出现“交易行”只证明导航文字存在，不能证明已经进入普通物资交易行。本文复刻对象是 **曼德尔相关入口中的典藏外观、我的关注与枪皮卖单**。
4. 原记录同时有原始 OCR 的局部 `location` 和归一化 `region/box/center`；日志中的 ROI 表达式不总等于实际物理像素矩形。参见第 7 节。

后续实现应保留 `legacy_page_label` 以对照原日志，同时记录实际锚点和页面子状态。**这只是避免把日志标签误读成画面，不改变业务顺序。**

### 4.1 收藏前的关注预检，是这次补回的关键遗漏

可复核的原始短序列：

P1:28  当前页面: None
P1:29  OCR: 暂未添加任何关注的皮肤

复刻应先保留这段判定顺序。**“关注为空”可以证明返回筛选；“先清空关注”没有证据；“关注非空总是跳过所有规则复核”也没有完整证明。**不要把缺证据的动作补进去。

### 4.2 任务分组，不等于按 INI 每行机械循环

P1 同一赛季先“查找2个”，再“查找11个”；之后依赛季转换又出现3个、1个等批次。可以确认存在批次化查找与赛季级组织，但还没有恢复分组键的完整实现。

已保存的 `config.ini` 是后期快照：15 条任务、6 个不同商品名称；P5 开始查找12个物品，P1 又有其它历史任务。因此不得用当前 15 条 INI 逐项解释更早日志。复刻时保留 **运行任务快照、筛选组、组内未完成商品、商品内成色规则、卖单扫描游标** 五个层次；分组比较键与稳定排序须由后续证据落定，不随意按自己的偏好排序。

### 5.1 时间行为必须忠实记录，但不能猜公式

原记录明确存在“超过阈值，正在设置系统时间”“系统时间设置成功”“偏移量已重置”。P1:1810 的偏移为696.740ms，2194为7.410ms；P3:26的1.668ms在允许范围内。**这证实存在阈值分支，不足以唯一恢复阈值、符号处理与自适应公式。**

P1:2375的原文字面为“本次延迟0.839ms”，后期配置 `clicktime=0.847`、`clicktime2=0.857`。先保留原值和原单位字符串，不擅自统一乘1000或认定是0.839毫秒。此前新架构的“不修改系统时间”属于独立工程决策，并不是原程序行为；对照表要明列这项差异。

### 5.2 关注上限：现在多了一条现场数值证据

P1:1795确有 OCR **“我的关注：48/150”**。这比“完全没有上限数值线索”更具体，但仅证明该历史画面显示150，不能升级成所有版本/账号的永恒上限。复刻判断以实际关注状态、满额反馈和当前画面容量为依据，不把150写成无条件常量。

## 9. 复刻约束与本次修正清单

### 9.1 固定下来，不再临时换业务入口

1. 原入口是“当前页识别与恢复”，不是普通物资交易行。
2. 典藏首页后的关注预检必须保留；空关注才有本例的返回筛选路径。
3. 已处于皮肤列表时保留接续分支，不能强制回到收藏第一步。
4. 保留赛季组、批次、商品、成色规则、卖单五层进度，不把任务INI一行等同于所有导航的起点。
5. 保留“读当前值→必要时改→看结果”，不是连续盲点一串按钮。
6. 收藏匹配、收藏回执、确认发起、成交结果分开；不得把历史日志计数当订单计数。
7. 程序界面不重做；底层采集/OCR可以独立实现，但不借此改动作顺序、筛选含义或入口分派。
8. 用户明确要求的图像不落盘、按步骤采集、验证后IDE前台继续生效；这些是本项目的明确差异，不伪称原程序本来如此。

### 9.2 下一批具体开发应按此顺序

| 先后 | 对照原流程的开发任务 | 验收方式 |
|---|---|---|
